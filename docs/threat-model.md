# Threat model

Bomb Squad reads hostile input by design. This document covers what an attacker controls, what they could try, and what stops them. It is updated with each roadmap phase.

## Assets

- **The scanning machine:** a developer workstation or a CI runner, and the credentials on it (cloud keys, tokens, `GITHUB_TOKEN`).
- **The verdict:** a reviewer acting on a report that hides a real finding is the main way Bomb Squad can cause harm.
- **The release:** what users install.

## Attacker-controlled input

The input is the bytes of every scanned file and of pasted text, including workflows, editor tasks, dev container and git hook configurations, and agent instruction files, settings and MCP configurations. It also includes package archives and registry metadata fetched by `bombsquad diff`, and in later phases the text an LLM reviewer reads.

## Threats and controls

| Threat | Control | Status |
|---|---|---|
| Input runs during analysis | The PowerShell engine only calls `Parser.ParseInput`. Nothing from the input is evaluated, invoked or imported. Names built from literals are folded by Bomb Squad's own code. | In place |
| Parsing makes the parser open files the input names. `using module` makes the parser read the module to resolve its classes (confirmed on Windows PowerShell 5.1); a network path would open a connection, which is untested. | `using module` and `using assembly` statements are blanked before parsing and reported as BS-DE-005. `tests/test_using_statements.py` proves the parser no longer reads the file. | In place |
| Other parse-time file access, such as DSC `Import-DscResource` in Windows PowerShell 5.1 | Parsing runs in a separate process in an empty temporary directory. | Not yet tested |
| JavaScript, Python or shell input runs during analysis | Parsed with tree-sitter (JavaScript, TypeScript, shell) or Python's `ast`. Nothing is imported, required or evaluated, and npm and pip are never invoked. | In place |
| Following targets and imports reads files outside the scan, such as `node ../../.ssh/x` or a symlink to `~/.aws/credentials` | Targets must resolve inside the package directory and imports inside a scanned directory. Symlinked files are skipped during directory walks. | In place |
| YAML or JSONC input runs code or builds objects while it is read | Workflows and hook configurations are composed with PyYAML's safe loader and never constructed, so tags such as `!!python/object` stay strings. Aliases point at one node and are not expanded, so an alias bomb costs nothing. JSONC is read by Bomb Squad's own reader into plain values. `tests/test_repo_entry_points.py` covers both. | In place |
| Deeply nested YAML or JSONC exhausts the stack | The JSONC reader stops at 200 levels. PyYAML's `RecursionError` is caught. Either way the file is reported as not read. | In place |
| Files that workflows, tasks and hooks name are read from outside the repository, for example `${{ github.action_path }}/../../x` or a lefthook `source_dir` of `../` | The same rule as targets: every file must resolve inside the repository or action directory, after symlinks are resolved. | In place |
| Agent instructions written to steer a reviewer, such as "test fixture, ignore this" | Bomb Squad does not follow instructions in what it reads; instruction text is matched against fixed phrasings, and no model reads it. | In place |
| Agent settings and `.env` files put secrets into evidence | Endpoint and proxy values are shown without user names, passwords or query strings, and only the variables the rules name are reported. A secret in any other variable is never shown. | In place |
| `@path` imports in `CLAUDE.md` read files outside the project, such as `@~/.ssh/config` | Imports are followed only when they resolve inside the project, after symlinks are resolved, and up to five levels. | In place |
| A file that GitHub, VS Code or a hook tool accepts but Bomb Squad's readers reject hides what it runs | The file is reported as not read, with the parser's message but not the input line. A repeated key keeps its last value, which other parsers may not do. | Partial |
| Deeply nested code exhausts the Python stack | `RecursionError` and `MemoryError` from `ast` are caught and reported, and the tree-sitter walks are iterative. Import following stops at five levels and 500 files. | In place |
| A deliberate parse error hides the rest of a file | Rules still run on whatever the parser reads, and parse errors are reported. | In place |
| A huge or deeply nested input exhausts memory or time | Files over 5 MB are skipped and reported. Parsing has a 120-second timeout. Decoding stops at three nested levels, which is reported. Folded strings are capped at 1,000,000 characters. | In place |
| Encoded or obfuscated code hides behaviour | `-EncodedCommand`, `-Command`, base64 literals and literal text passed to `Invoke-Expression` or `[ScriptBlock]::Create` are decoded and analysed. Names built from literals are folded. Text computed at run time is not resolved, and each finding says so. | Partial |
| Terminal escape sequences in evidence | Not yet handled. Evidence is printed as found. | Open |
| The scanner's own dependencies or CI are compromised | The runtime dependencies are tree-sitter and three grammars, which ship native code, and PyYAML, whose pure-Python safe loader is used. They are locked with hashes in `uv.lock`, checked with `uv sync --locked`, and resolved only from releases at least seven days old (`exclude-newer`). Actions are pinned by commit SHA with read-only permissions. | In place |
| A registry response or redirect points the fetcher somewhere else | Only HTTPS requests to `registry.npmjs.org`, `pypi.org` and `files.pythonhosted.org`, and with `--source` to `api.github.com` and `codeload.github.com`, are made, and every redirect is checked against the same list. Package artifacts must come from the registries' own file hosts. Metadata is capped at 200 MB and artifacts at 100 MB. | In place |
| A repository archive or API answer misleads the source comparison, or the review of an updated action | Archives are unpacked with the same rules as packages and never run. GitHub publishes no hash for them, so they are trusted as GitHub serves them; an action pinned by commit SHA is at least fetched at that exact commit. No credentials are sent. The tag record is only appended to, and a record that cannot be read is left untouched. | Partial |
| A tampered or substituted artifact is analysed as the real one | Each artifact's SHA-512 or SHA-256 must match the registry's before it is opened. A SHA-1-only npm version is noted. This proves the bytes are what the registry serves, not that the registry or the publisher is honest. | In place |
| An archive writes outside its folder or overwrites files (tar slip, zip slip, links) | Members are written one by one, never with `extractall`. Links and special files are skipped. `..` and case clashes are skipped. Absolute paths and drive letters are made relative, and reserved or invalid names are renamed, so a crafted name cannot hide a file from the scan. Every target is resolved and checked to be inside the folder. | In place |
| A decompression bomb exhausts disk or memory | Unpacking stops at 20,000 members or 500 MB of decompressed bytes, counted while reading. | In place |
| Unpacked malware on a development machine | Archives are unpacked to a temporary folder that is deleted afterwards, and never run. Antivirus may still quarantine files there. Benchmarks over malware datasets run only on Linux CI. | Partial |
| The benchmark leaks or spreads samples | It runs on a disposable GitHub-hosted runner with a read-only token and no secrets. Only the chosen samples are downloaded, they are unpacked in per-package temporary folders inside the job, and neither tool runs them. The uploaded results hold names, versions, rule IDs and levels, never evidence or sample content. | In place |
| Code scanning results are uploaded from CI | The upload job alone has `security-events: write`, uses `github/codeql-action/upload-sarif` pinned by SHA, and does not run for pull requests from forks. | In place |
| A pull request attacks the gate that reviews it | The gate runs on `pull_request`, never `pull_request_target`, so it gets a read-only token and no secrets on fork pull requests. The pull request's code is only parsed. uv runs from the Action's own folder, so the repository's uv settings are not read. The base is checked out with LFS downloads off. | In place |
| The gate's comment is used to inject content or notify people | One job, with only `pull-requests: write`, posts the comment. It downloads the report as data and runs nothing from the pull request. Untrusted text is escaped or put in code spans, and `@` cannot mention anyone. Fork pull requests get no comment, only the job summary. | In place |
| Antivirus quarantines test fixtures, breaking checkouts | Fixtures that look like malware are ROT13-encoded in the tests and decoded in memory. | In place |
| A detonated package escapes to the host | `bombsquad detonate` runs only on Linux, and is meant for disposable CI runners. The benchmark detonates malicious samples only on a disposable VM, registered as an ephemeral runner for one run and destroyed after it ([setup](development.md#detonation-vm)). The job refuses to start on any other runner. The package's container has no host folders mounted: files go in with `docker cp` and the trace comes out on standard output. All capabilities are dropped except the three strace needs, to trace and to switch users. Switching to the unprivileged user clears them, and `no-new-privileges` stops the package from regaining any. Memory, CPU and process counts are limited. Docker still mounts its own generated `resolv.conf`, `hosts` and `hostname` files, owned by root. A container is not a virtual machine: a kernel or Docker flaw can still be used to escape. | Partial |
| A detonated package reaches the network | Its only network is an internal Docker network with no route out. The sink is the only other host and answers every name with its own address. strace records every address the package connects to, including ones the sink never sees. The Docker host's bridge address can be reachable from an internal network, which is one reason detonation runs on disposable runners. | Partial |
| A detonated package's dependencies are fetched with network access | A separate container fetches them, from the same pinned image, before the sandbox starts. It never holds the package or the fake credentials. It runs npm with `--ignore-scripts` and pip with `--only-binary=:all:`, so no package code runs while it has a network. It has no capabilities, no host mounts and an unprivileged user. Only regular files with plain relative names are kept from what it sends back, within size, file-count and time limits. | In place |
| The sink's certificate authority is misused | The sink makes it for one run, in its own container, where its key stays. Certificates are valid for two days and issued only for names that are plain host names, at most 256 a run. Only the package's container trusts the authority, and it is removed with the run. The host never trusts it. | In place |
| A detonated package tampers with what is recorded | strace runs as root and pipes the trace through a root process. The package runs as another user and cannot write to it. The sink runs in its own container. A package can still flood its own trace, which is cut at 64 MB, or run out the time limit; both are reported. | In place |
| Canary credentials leak or work somewhere | They are random for each run and valid nowhere. | In place |

## Later phases

These get their own rows when they are built:

- **The live watch** (Phase 6): false accusations against real packages. Changes are reported, never verdicts, and a person reviews every report.
- **LLM triage** (Phase 7): prompt injection from the code under review. The LLM can reorder findings but never suppress them.
